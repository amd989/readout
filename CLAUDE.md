# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

Readout is a companion app for the EEVblog 121GW multimeter over Bluetooth LE, built with .NET 10 and .NET MAUI. It's open source (MIT) and meant for the App Store, Google Play and the Microsoft Store, with a Linux build on MAUI's preview GTK4 backend.

- `Readout.Core/` (plain `net10.0`, warnings are errors): the protocol (`Protocol/`: `MeterPacket`, `PacketFramer`, `MeterCommands`, `MeterBluetooth`), LCD decoding (`Display/`: `ReadingDecoder`, `ModeInfo` range tables, `SiFormat`), logging and CSV (`Logging/`), the simulated meter (`Simulation/`), and the connection contract plus session (`Connection/`: `IMeterConnection`, `SimulatedMeterConnection`, `MeterSession`). No MAUI or Bluetooth stack here.
- `Readout/`: the MAUI app. `Services/BleMeterConnection` implements `IMeterConnection` over Plugin.BLE. `ViewModels/` use CommunityToolkit.Mvvm. `Drawing/` draws the LCD (`LcdDrawable`, `SevenSegment`) and the trend graph with MAUI Graphics.
- `Readout.Core/Logging/`: `MeasurementLog` (the live log), `SampleCsv` (the CSV format, written and read), `SessionStore` (saved sessions: `{id}.csv` + `{id}.json` in the app data folder), `RecordingAutosave` (appends the live log to `recording.csv` every 10 s and on sleep, restored at launch). `Display/TrendWindow` is the graph's zoom and pan; `Display/TrendBucket` groups long logs into time slots (the graph draws each slot's average as the line over a faint min/max band, so noisy readings don't fill the plot).
- `Readout.Core/Feedback/`: `ContinuityAlert` (on/off with hysteresis for continuity and resistance) and `ToneWave` (the looping beep). `Readout/Services/ContinuityFeedback` plays it through `ContinuityTone` (per platform) and vibrates; `AppSettings` holds the Settings tab's values in Preferences.
- Navigation is a Shell `TabBar` (Meter, Sessions, Settings). On iOS and Mac it gets no Shell colors on purpose, so iOS 26 draws the system Liquid Glass bar; Android and Windows get the `BrandShell` style.
- `Readout/Views/TrendView` is the graph control (pinch, drag, double-tap when `Interactive`; `RecentSeconds` limits it to the newest stretch, as on the meter page); `GraphPage` is it full screen, `SessionsPage` and `SessionDetailPage` list and show saved sessions.
- `Readout.Mcp/` (plain `net10.0`): the MCP server for AI assistants. `MeterTools` are the tools (results are source-generated JSON, so trimming is safe; meter access goes through `IUiThread` to the main thread). `McpHttpServer` serves them with the MCP SDK's stateless `StreamableHttpServerTransport` over `LoopbackHttp`, a minimal HTTP/1.1 on a loopback `TcpListener`. Not HttpListener: it does a DNS lookup on start that hangs in the Mac sandbox. Referenced by the app on Mac Catalyst and Windows, and by the Linux head; `Readout/Services/McpHost` starts and stops it from Settings. See `docs/MCP.md`.
- `Readout.Linux/`: the Linux head (see Linux below). `BlueZ/` is the meter connection over BlueZ; the other files fill gaps in the GTK backend.
- `Readout.Tests/`: xUnit v3 tests for the core and the MCP server (end to end with the SDK's client), plus the Linux head's `BlueZNames` and `RecentRssi`, compiled in as linked files (they must stay free of D-Bus and GTK).
- `docs/PROTOCOL.md`: the packet format. Read it before touching `Protocol/` or `Display/`.

The protocol is ported from the official EEVblog app's `PrivatePostRelease` branch (https://gitlab.com/eevblog/app-121gw, MIT, David Ledger), and matches EEVblog's "Revised Packet Format Blob V2" document. Its `master` branch has an obsolete 52-character text parser; ignore it. Keep the David Ledger credit in THIRD_PARTY_NOTICES.md and the About page.

## Commands

```bash
dotnet test --project Readout.Tests
dotnet build Readout -f net10.0-ios -p:RuntimeIdentifier=iossimulator-arm64
dotnet build Readout -f net10.0-maccatalyst
dotnet build Readout -f net10.0-android
./deploy-ios.sh        # physical iPhone; device names come from .devices (git-ignored)
./deploy-mac.sh        # build and launch the Mac app (--log follows its output)
./deploy-windows.ps1   # build and launch the Windows app (Debug, unpackaged), replacing a running copy
./publish-ios.sh       # Release .ipa for TestFlight / App Store (fails on any non-arm64 slice)
./publish-mac.sh       # Release .pkg for the Mac App Store (universal, sandboxed)
./publish-windows.ps1  # Release .msix (x64 + arm64) for the Microsoft Store; -Test -Install for a local copy
./publish-android.sh   # signed Release .aab for Google Play + .apk (needs the ANDROID_* keystore variables)
git tag v1.2.0 && git push origin v1.2.0   # release.yml: every store + a GitHub release (docs/STORE-CI.md)
dotnet build Readout.Linux       # the Linux head (plain net10.0, builds on the Mac too, no workload)
./publish-linux.sh x64 arm64     # self-contained Readout-linux-<arch>.tar.gz in Readout.Linux/bin/publish/
```

## Things to know

- `MeterSession` raises its events through `Dispatch`, which the app sets to the main thread. The log is only touched there.
- Simulators have no Bluetooth: Debug builds on a simulator or emulator (or with `READOUT_FAKE_BLE=1`) scan the simulated meter. "Try the demo meter" exists in every build, for App Review, which has no 121GW.
- Per-machine settings stay out of git: `Directory.Build.local.props` (Mac Debug code signing; see the `.example`) and `.devices` (iPhone UDIDs for `deploy-ios.sh`).
- The name "121GW" belongs to EEVblog. Use it only to say what the app works with ("for the 121GW"), never as the app's name or in its icon.
- After editing an `Info.plist`, build with `-t:Rebuild`: an incremental build can keep a stale compiled plist.
- `docs/` is also the GitHub Pages site (plain HTML and `style.css`; `.nojekyll`). The App Store listing's support, marketing and privacy URLs point at it, so keep `privacy.html` in step with `PRIVACY.md`. `store/screenshots/` has the full-size App Store screenshots: iPhone medium display 1206x2622 (the size App Store Connect requires), iPhone large display 1320x2868, iPad 13", Mac 2880x1800, Windows 1920x1080 (the demo meter, dark mode), all without an alpha channel. The listing text and submission checklist (`store/*.md`) are kept local and git-ignored; `docs/screenshots/` has smaller copies for the web.
- The Mac app's sandbox container is tied to the signature that first used it. A build signed with a different certificate (Release vs Debug, TestFlight) hangs at launch in `_libsecinit_appsandbox`, with no window, until the user answers macOS's access prompt; scripts can't read the container meanwhile ("Operation not permitted").
- Windows: Debug builds are unpackaged (plain .exe); Release builds are MSIX. The architecture comes from `WindowsRuntimeIdentifier`, not `-r` (which would apply to Android too). The Store needs the version's last part to be 0, so `publish-windows.ps1` passes `ApplicationDisplayVersion=major.minor.build` and `ApplicationVersion=0` (MAUI puts `ApplicationVersion` last). The package identity in `Platforms/Windows/Package.appxmanifest` must match Partner Center's Product identity.
- App Store Connect rejects any x86_64 slice in an iPhone build (ITMS-90087; Wavelength hit it through SkiaSharp). `publish-ios.sh` checks every binary in the .ipa; if a new package brings a fat framework, strip it before signing as Wavelength's `_ThinFrameworksForDevice` does.

## Linux

MAUI has no Linux TFM, so `Readout.Linux` is a plain `net10.0` head on Microsoft's GTK4 backend (`Microsoft.Maui.Platforms.Linux.Gtk4` and `.Essentials`, 0.1.0-preview.13 from dotnet/maui-labs, which defines `LINUX`). It compiles `../Readout`'s sources, XAML and resources as linked items (everything but `Platforms/`), so new shared files reach Linux without touching it. `MauiProgram`'s `#if LINUX` branches pick the GTK host and Essentials, the BlueZ connection and console logging. The pattern, and `PageRelayout`, `GestureWiring`, `BlueZBus` and the Docker setup, come from the user's Wavelength app (its branch `claude/linux-support-08d2f0`).

- MAUI's `MainThread` throws on Linux: use `Services/UiThread` (it posts through the app's dispatcher there). Essentials statics work only after `Build()`, so resolve them in service factories, not while configuring the builder.
- `READOUT_FAKE_BLE=1` works in Release on Linux, so the published app can be tried without a meter. The MCP section of Settings always shows there.
- Gaps in the backend (preview 13) that the head fills, each in its own file, registered in `Program`: `PageRelayout` (a page is laid out only when its allocation changes, so a view that later appears or changes size keeps stale bounds; the meter's battery line, filled in after connecting, drew at the top left now and then: a measure and arrange of the page is queued on `MeasureInvalidated`, on any view's `Width`/`Height` mapping and on the page's `SizeChanged`); `GestureWiring` (gesture recognizers were never attached, so taps on list rows did nothing); `ShellHeaderBar` (Shell is only a notebook of tabs: no back button, title or toolbar items, and route navigation to another tab didn't switch the tab; this puts a `Gtk.HeaderBar` in the window's title bar, with Escape and Alt+Left for back); `TrendMouse` (tap ignores `NumberOfTapsRequired`, pan looks for a `SendPan` MAUI 10 doesn't have, pinch has no origin: the graph gets wheel zoom, drag to pan and double-click reset); `KeyButtonPress` (Button never raises `Pressed`, so meter keys had no long press: it follows the GTK button's active state, and a press let go off the button is cancelled). `FileSaveDialog` replaces Share for CSV export (Share there is `xdg-open`). `WindowFit` caps the window's opening height at the first screen's height less room for a panel (GTK can't tell where panels are), so it fits the 1280×800 laptop; the meter page scrolls for the rest. `tools/linux-test` takes `-e SCREEN=1280x800x24` to try a small screen.
- Known gaps: alerts show no title, no continuity beep or vibration, tabs are text only (the backend draws no tab icons), and GTK logs harmless `gtk_widget_size_allocate` warnings at startup.
- BlueZ (`BlueZ/`): `BlueZBus` is a few hand-written calls over Tmds.DBus.Protocol. `BlueZMeterConnection` discovers with a filter of LE only and `DuplicateData`, and lists devices whose Name or Alias looks like a meter; a meter's id is its address. Connect is `Device1.Connect`, waiting for `ServicesResolved`, picking the data characteristic (`BlueZNames.PickDataCharacteristic`, the same rule as on other platforms), then `StartNotify`: indications arrive as `Value` changes, framed by `PacketFramer`. Keys are `WriteValue` as a request. It waits (up to 2 s) for the adapter's `Discovering` to turn false before `Device1.Connect`, and retries an aborted connect twice: `StopDiscovery` returns while the kernel is still taking the scan down, and an LE connect started meanwhile is cancelled with `le-connection-abort-by-local` before the controller is asked to connect (every connect on the Fedora laptop failed that way; `mock-bluez.py` now does the same). While scanning it logs how many devices it has heard and each meter it finds. Before connecting it sets `Device1.PreferredBearer = le`: BlueZ connects a device it takes for dual-mode over Classic Bluetooth (on Fedora, Wavelength's Linux build got Classic links to a Mac and ended up paired, with the Mac playing its sound through the laptop). The property exists only with `bluetoothd -E` (BlueZ 5.80+), and only on devices BlueZ takes for dual-mode (the meter, LE-only, answers `UnknownProperty`); without it the app logs whether the meter's advertisement says LE-only (`BlueZNames.IsLeOnly`: a random address or the "BR/EDR not supported" flag). The 121GW's Bluegiga radio is LE-only, so a Classic attempt can only fail (a `br-…` error, logged with the fix), not pair. Readout connects only to devices named like a meter, never to phones or computers. BlueZ invalidates RSSI when discovery stops and has no D-Bus call to read it on a connection, so `RecentRssi` keeps the scan's value for 30 s and then reports none (the signal bars hide). No system bus or no adapter is `BluetoothState.Unavailable`, an unpowered adapter `Off`.
- Check it in Docker on the Mac with `tools/linux-test/` (Ubuntu 24.04, GTK 4.14, Xvfb; Docker's VM has no Bluetooth): `docker build -t readout-linux-test tools/linux-test`, `dotnet publish Readout.Linux -c Release -r linux-arm64 --self-contained -o <dir> -p:DebugType=none` (arm64 is native on Apple silicon), then `docker run -d --name ro -v <dir>:/app -v <out>:/out readout-linux-test <mode>`, with a new `<out>` folder each run (Docker Desktop kept serving a deleted one). Modes: `fake` (simulated meter), `mock` (the BlueZ code against `mock-bluez.py`, a stand-in bluetoothd that plays a 121GW: it indicates real packets split across indications and logs key presses to `/out/mock.log`; `dbus-send --system --dest=org.bluez / org.readout.Mock.Drop` takes it out of range for 8 s, `org.readout.Mock.Power boolean:false` powers the adapter off), and `none` (no system bus). The app's log is `/out/app.log`. Screenshot with `docker exec ro bash -c 'DISPLAY=:99 import -window root /out/s.png'`, click with `xdotool mousemove X Y click 1`. The window is 480×1000 at the top left: Connect at (403, 132), the first scan result at (200, 185), tabs at y 69, the header bar's back button at (27, 26). The MCP server is reachable inside the container with curl; the token is in `/root/.config/Readout/preferences.json`.
- The Fedora laptop (also used for Wavelength): `ssh darwin@192.168.1.77`, Fedora 43 on x86_64, KDE on Wayland, GTK 4.20, BlueZ 5.87 running with `--experimental` (so `PreferredBearer` works) and without its battery plugin. Deploy with `./publish-linux.sh x64`, copy the tarball over and unpack it into `~/readout-test/`, then start it on the desktop with `cd ~/readout-test && WAYLAND_DISPLAY=wayland-0 XDG_RUNTIME_DIR=/run/user/1000 DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus setsid -f ./readout/Readout > app.log 2>&1 < /dev/null` (without `setsid` the ssh session never returns). Stop it with `pkill -x Readout`. `spectacle -b -n -f -o <file>` takes a screenshot (with the same variables). Nothing there can click for you.
- Tested Oct 31 on the Fedora laptop with the real 121GW (6C:5C:B1:CE:9F:AA, Silicon Labs, public address, flags 0x06, the Bluegiga serial service `0bd51666-e7cb-469b-8e4d-2742f1ba77cc`): found, connected in about 2 s, live readings and the graph, short presses (MODE changed the mode) and long ones (REL turned on 1kHz), dial changes followed, and it reconnected by itself within a second when the meter's Bluetooth came back on. The meter turns its Bluetooth off by itself after a while; hold 1ms PEAK to turn it on again.
